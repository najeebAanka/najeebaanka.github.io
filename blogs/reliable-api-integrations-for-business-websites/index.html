Building Reliable API Integrations for Business Websites

By Najeeb Anka

In this article

Define the handover before writing code Keep private credentials on the server Treat failures as part of the normal flow Prevent retries from creating duplicates Test more than the successful request Give someone ownership after launch

An integration is only useful when information arrives in the right place and the team knows what happens when it does not. Whether you connect an enquiry form to a CRM or an order to a fulfilment service, the work extends beyond sending a successful request.

Define the handover before writing code

Describe the business event that starts the integration, the information being sent, and the system responsible for each record. For example, a submitted enquiry might create a lead in a CRM and store the CRM identifier alongside the original submission.

Map each field explicitly. Decide how names, phone numbers, optional fields, and source tags should be represented. Agree on what happens if the destination rejects a value rather than silently dropping it.

Keep private credentials on the server

A browser downloads the JavaScript used by a website, so it cannot keep a private API key secret. Calls that require confidential credentials should go through a controlled backend or a suitable hosted integration service. Restrict the credentials to the access the integration actually needs.

A static website can still link to public services and use APIs designed for public browser access. The distinction is whether the operation requires a secret, privileged access, or a trusted decision that a visitor should not be able to alter.

Treat failures as part of the normal flow

Set a timeout and distinguish a rejected request from a temporary connection problem. Keep a record of the intended operation so a temporary outage does not make an enquiry disappear. Show visitors a status that accurately reflects what has been accepted.

An HTTP 429 response indicates rate limiting. The server may include a Retry-After header to guide the next attempt; see the MDN explanation of 429 responses. Space retries out, limit their number, and route persistent failures to someone who can investigate.

Prevent retries from creating duplicates

A timeout does not always mean the destination rejected a request. It may have created a record before the response was lost. Repeating that operation can create a second record unless the integration accounts for it.

POST requests are not guaranteed to be idempotent: repeating one can produce another side effect. Where supported, use the provider’s documented idempotency mechanism. Otherwise, design an appropriate unique reference and reconciliation process instead of assuming retries are harmless.

Test more than the successful request

Use the provider’s sandbox when available and create a small set of realistic scenarios. Verify that the visitor experience and the receiving system agree about what happened.

  • A valid submission creates the intended record.
  • A missing or invalid field produces a useful error.
  • A timeout is recorded and handled without an endless retry loop.
  • A repeated submission does not create an unintended duplicate.
  • An expired credential creates an actionable operational alert.

For incoming webhooks, follow the provider’s verification instructions and account for repeated events. Treat incoming data as untrusted until it has been checked.

Give someone ownership after launch

Record request identifiers, outcomes, and enough context to diagnose failures while avoiding unnecessary personal data in logs. Agree on who receives alerts and who can replay or reconcile a failed operation safely.

Design for recovery: a reliable integration should make it possible to answer three questions: what was supposed to happen, what actually happened, and what should happen next?

Useful integrations are maintained business processes. Keep the field mapping, account ownership, and recovery procedure documented alongside the code so the connection remains understandable after launch.
