Practical Laravel Performance Improvements: Measure First

By Najeeb Anka

In this article

A slow Laravel application rarely improves through a collection of unexplained tweaks. Start with a real request, identify where its time is spent, and change one meaningful bottleneck at a time. The goal is a repeatable improvement you can measure and maintain.

Establish a baseline for a real journey

Choose a route that matters to users, such as a property listing, search result, or customer dashboard. Record its response time, database query count, and external calls using representative data. Repeat the measurement so an unusually fast or slow request does not become your only evidence.

Separate server response time from the time the browser spends downloading and rendering the page. A quick server response will not fix an oversized hero image, and compressing an image will not resolve a slow database query.

Look for repeated database queries

A list page can quietly request related data once for every displayed item. As that list grows, the number of queries grows with it. Laravel’s Eloquent documentation explains how eager loading helps address the N+1 query problem.

Inspect the relationships the page actually uses, load them deliberately, and check the resulting query count. Avoid loading every available relationship: unnecessary rows and columns still consume memory and database time.

Reduce the amount of work in each request

Use pagination for large collections and fetch the information needed for the visible interface. Review expensive filtering, sorting, and repeated calculations. Check query plans before adding indexes so the change matches the query you are trying to improve.

For a dashboard, ask whether all panels need to be calculated immediately. A smaller initial response and a clear loading state may serve the user better than waiting for several unrelated reports before displaying anything.

Cache with an explicit freshness rule

Cache data that is expensive to produce and acceptable to reuse. Laravel’s cache documentation describes retrieving a stored result or generating it when it is absent.

Before adding a cache, decide how long the information may be reused, what should invalidate it, and whether the key must distinguish users or filters. Shared cache entries must not expose one user’s private information to another. Test changes to the underlying data as well as the initial cache hit.

Move suitable tasks out of the response path

Generating a large export or processing a background notification may not need to block the current page. Laravel queues support deferred job processing, provided the application has an appropriate queue connection and running worker.

Account for delayed completion, failed jobs, and worker operations. A job that has been accepted is not the same as one that has finished. Keep work synchronous when the user needs its result immediately to make the next decision.

Re-measure and protect the improvement

Run the same journey with comparable data after each change. Record both the result and any trade-off, such as a period of cached data or a newly required background worker. Check that the faster route still returns the correct information.

  • Did the measured bottleneck improve?
  • Does the route behave correctly with a larger dataset?
  • Are errors and background failures visible?
  • Can someone explain the cache and queue behaviour?
A practical order: measure the request, inspect queries, reduce unnecessary work, consider caching, then assess background processing. Choose the next step from the evidence.

Performance work is most useful when it leaves the application easier to understand. Keep a short record of the problem, the change, and the measurement so future work starts from evidence rather than guesswork.
